# 无证门店 / 地摊收款与分账方案

> 面向本仓库「万业互联云」：地摊（stall）可无营业执照、无食品经营许可证入驻；异业/供应链需执照。  
> 问题：无证主体如何跑通收款？能否直接套用平台微信支付做分款？怎样落地又控风险？  
> 结论先行：**产品入驻与台账抽成已可跑通；真实微信分账不能「无资质共用平台商户号随便分」**，必须按主体类型选路径，并优先落地「合规分层 + 收付通二级商户 / 个人经营者」组合。

---

## 1. 项目现状（代码与产品口径）

### 1.1 入驻资质（已实现）

| 经营类型 | 营业执照 | 食品经营许可证 | 必填材料 | 代码口径 |
| --- | --- | --- | --- | --- |
| 地摊 `stall` | 可不提供 | 可不提供（选填） | 身份证正反面、摊位照、勾选合规承诺 `stallCommitment` | `applyService.ROLE_LICENSE_RULES`；路径标记 `stallPath=no_license_personal` |
| 异业 `cross` | 必填 | 业务上建议有（食品类） | 执照、法人证、门店照、信用代码 | 同左 |
| 供应链 `supply` | 必填 | 视品类 | 同异业 | 同左 |

运营台已识别「地摊无证路径 / 无证个人经营者」。

### 1.2 收款与分款（当前逻辑）

现金相关主路径（地摊点餐 / 扫码收款 / 异业兑换现金部分）：

1. 下单 → `wxService.buildPayResult`  
2. **未配商户密钥时走 `wxpay_sim`**：业务上直接记「已支付」  
3. 本地抽成：`commissionService` → `commission_ledger`  
4. 商户净额入账：`merchant_accounts.cash_settlement`  
5. 商户提现申请 → 运营/创始人审核 → 人工打款（非微信自动分账）

关键事实：

- 字段与清单已预留 `merchants.wx_sub_mch_id`、服务商 / 平台收付通方向（见 `docs/支付与入驻开通清单.md`）。
- **真实 JSAPI 预下单、支付回调验签、微信分账 API 尚未完整接通**；钱不会自动进店主微信零钱/银行卡。
- 「平台抽成」目前是**业务台账**，不等于微信侧 profit_sharing 已发生。

### 1.3 直接回答两个问题

| 问题 | 答案 |
| --- | --- |
| 无执照、无食品证的地摊，能否用**现有这套业务逻辑**跑通收款？ | **能跑通「业务闭环」**：入驻 → 扫码/点餐 → 模拟或真实支付成功后记订单 → 抽成台账 → 余额 → 提现审核。无证不挡地摊入驻与下单。 |
| 能否申请「用平台的微信支付」给无证摊位**自动分款**？ | **不能简单理解为：钱进平台一个商户号再随意分给无证个人。** 微信侧要求收款主体可识别、可结算；无证主体通常只能走「个人经营者 / 小微」等允许的进件类型，或走平台统一收款+合规结算（对平台牌照与资金安全要求更高）。**当前代码的分账是账本级，不能替代微信合规分账。** |

## 2. 风险地图（平台必须正视）

| 风险类型 | 无证地摊场景表现 | 对平台后果 |
| --- | --- | --- |
| 支付合规 | 用平台商户号代收再私下分给个人 | 二清嫌疑、商户号处罚、关停 |
| 食品与市监 | 现制现售食品无许可 | 监管处罚牵连平台；客诉与舆情 |
| 税务 | 大量个人收款无完税路径 | 商户与平台税务争议 |
| 洗钱 / 套现 | 无证主体难 KYC、难追责 | 微信与银行风控拒付、冻资 |
| 消费者 | 食品安全、售后无主体 | 退款纠纷落在平台 |

原则：**业务上可以「先让地摊用起来」，资金上必须「主体可结算 + 限额 + 可追溯」**，不能用模拟支付的产品体验惯性直接上真实大额代收。

## 3. 方案对比（结合本项目）

下列方案均可与现有「积分发放 / 采购额度 / 抽成台账 / 提现审核」共存；差异在**现金怎么进、怎么给到摊主**。

### 方案 A · 平台台账结算（现状增强）——过渡期默认

**做法**

- 消费者仍对「平台服务商 / 平台自有商户」或暂用模拟支付；
- 订单成功后继续：`commission_ledger` + `cash_settlement`；
- 摊主提现走 `/merchant/withdraw`，运营人工打款到身份证同名银行卡 / 微信零钱（企业付款到零钱需另开权限）。

**适合**

- 灰度、沙井试点、日流水可控；
- 真实收付通 / 二级商户尚未开通时。

**优点**：与现码一致，落地最快。  
**缺点**：平台有资金沉淀与二清压力；人工打款成本高；不能对外宣传「微信自动分账到店」。

**风控要点**

- 单笔 / 单日 / 单月提现上限（建议地摊更严）；
- 提现必须同名：身份证姓名 = 结算户名；
- 无证摊位标记 `stallPath=no_license_personal`，后台强制人工审；
- 仅开放「已开城」区域。

**技术增量（相对现状）**

- 提现单增加：结算户名、银行卡号/OpenID、KYC 状态；
- 运营台提现审核与打款凭证上传；
- 对账：订单净额合计 = 账户变动 + 抽成。

---

### 方案 B · 服务商 + 平台收付通 + 二级商户进件（推荐主路径）

**做法**（与 `docs/支付与入驻开通清单.md` 一致）

1. 平台成为**微信支付服务商**并开通**平台收付通（或现行等价产品）**；  
2. 每个可收款商户进件拿 **二级商户号**，写入 `merchants.wx_sub_mch_id`；  
3. JSAPI 下单 `sub_mchid` = 该店；支付成功后资金入二级商户；  
4. 按约定**分账**给平台（抽成）+ 剩余留店 / 结算到店主账户；  
5. 本地仍写 `commission_ledger` 做业务对账。

**无证地摊怎么进件**

| 主体类型 | 材料方向 | 是否可无「食品经营许可证」 |
| --- | --- | --- |
| 个人经营者 / 小微（微信允许的个人收款主体） | 本人身份证、结算银行卡、经营场景照；按微信当页要求 | **进件不强制食品证**；但若售卖热食/餐饮，市监合规仍是摊主与平台的经营风险，需产品侧限制类目或催办许可 |
| 个体工商户 / 企业 | 执照等 | 食品类仍建议有许可 |

**适合**：异业、供应链、以及愿意补「个人经营者」材料的地摊。  
**优点**：最贴近微信合规；自动分款；平台不做二清。  
**缺点**：审核与进件周期长；部分无证个人可能被微信拒件。

**技术实现要点**

| 模块 | 内容 |
| --- | --- |
| 配置 | `WX_PAY_MCH_ID`、APIv3、证书、回调 URL（云托管） |
| 下单 | 真实 `payParams`；禁止无 `wx_sub_mch_id` 的商户走现金（可降级积分/仅展示） |
| 回调 | 验签、幂等、改订单、再入账与分账 |
| 分账 | 调用微信分账 API；失败重试与挂账 |
| 进件 | 后台录入或 API 同步 `wx_sub_mch_id` + 进件状态机 |
| 地摊 | 入驻通过后引导「开通收款」向导：补个人经营者材料 → 进件中 → 可收款 |

---

### 方案 C · 平台统一收款 + 延时结算（资金归集）——高风险，仅限小额试点

**做法**

- 所有无证摊位订单打到**平台商户号**；  
- 系统记各摊台账；T+N 提现审核后打出。

**问题**：极易被认定为支付机构未持牌的「二清」。  
**仅当**：法务确认可行、额度极低、主体清晰、且短期过渡——**不建议作为长期主方案**。

若被迫短期使用，必须：

- 合同写明「代收代付服务 / 交易担保」边界（仍不能替代支付牌照）；  
- 单笔 ≤ 限额、日累计限额、禁止提现到非同名账户；  
- 尽快迁移到方案 B。

---

### 方案 D · 混合分层（推荐落地组合）

按商户资质自动路由支付能力，与本项目三类商家天然契合：

```
异业 / 供应链（有执照）
  └─ 必须方案 B：二级商户进件 → 真实收款 + 微信分账

地摊 · 有个人经营者进件材料
  └─ 方案 B 子集：个人经营者二级商户 → 真实收款

地摊 · 暂无进件 / 仅有身份证+承诺
  └─ 方案 A：仅「开城试点」+ 低额台账提现
       或 禁止现金、仅积分核销 / 供应链采购相关（见方案 E）
```

产品规则建议写入配置（示例）：

| 字段 | 含义 |
| --- | --- |
| `pay_mode` | `sub_mch` / `ledger_only` / `cash_disabled` |
| `wx_sub_mch_id` | 空则不能真实现金（除非 ledger_only 且开城开关打开） |
| `stall_path` | `no_license_personal` / `licensed` |
| `daily_cash_limit` | 无证台账日限额 |
| `food_category_blocked` | 无食品证禁止上架热食类 SKU（可选开关） |

---

### 方案 E · 业务降维：无证不碰现金

**做法**

- 无证地摊：只展示菜单与积分发放，**不开放扫码现金收款**；  
- 现金能力留给已进件商户；无证摊主通过「帮用户攒积分 / 导流异业兑换 / 向供应链采购」获利（额度账户）。

**优点**：支付与食品风险最低。  
**缺点**：地摊核心「收款」卖点变弱，地推话术要改。

可作为「食品类无证」的强制策略：无食品证 → 禁止餐饮现制类目上架 + 禁止扫码现金。

## 4. 最优方案建议（结合本项目目标）

### 4.1 战略选择

**最优可规模化路径 = 方案 D（混合分层），中长期全部现金能力收敛到方案 B。**

理由：

1. 说明书与代码已承认**地摊无证入驻**，不能一刀切拒绝；  
2. 异业/供应链本就有执照，应直接走收付通二级商户，树标杆；  
3. 平台抽成模型（`commission_*`）与微信分账比例可对齐，避免两套账长期漂移；  
4. 无证个人用台账过渡，避免一上来二清。

### 4.2 「最好落地」的分阶段路线

| 阶段 | 目标 | 支付 | 地摊策略 | 验收 |
| --- | --- | --- | --- | --- |
| P0 现网 | 业务不断 | `wxpay_sim` / 台账 | 无证可入驻可下单；提现人工+限额 | 扫码收款、抽成、提现审核 |
| P1 合规底座 | 服务商+收付通开通 | 配密钥，仍可灰度真实支付 | 推「开通收款」补个人经营者 | 至少 1 家异业真实收款 |
| P2 分层上线 | 有 `wx_sub_mch_id` 才真实现金 | JSAPI+回调+分账 | 无进件 → `ledger_only` 或禁现金 | 抽成台账与微信分账抽查一致 |
| P3 收紧 | 取消无证大额台账 | 全面二级商户 | 催办个体户/食品许可；逾期降权 | 无证仅低额或禁现 |

### 4.3 规避平台风险清单（落地必做）

**资质与协议**

- [ ] 入驻协议 + 地摊合规承诺（已有勾选）留存时间戳与版本号  
- [ ] 明确：平台提供技术与撮合，食品安全与证照责任在经营者  
- [ ] 食品类无证：限制类目或强制提示「不得经营需许可食品」  

**支付与资金**

- [ ] 禁止「一个平台商户号长期代收全城无证摊」  
- [ ] 有二级商户号才开启真实 `wx.requestPayment`  
- [ ] 抽成走微信分账接收方，不私下挪资金  
- [ ] 台账路径严格限额 + 同名结算 + 人工审  

**运营与风控**

- [ ] 开城白名单；异常退款率 / 投诉熔断歇业  
- [ ] 无证摊位在运营台高亮；审核日志可追溯（可与 `apply_review_logs` 体系衔接）  
- [ ] 定期对账：微信账单 ↔ `consumer_orders` ↔ `commission_ledger` ↔ `merchant_accounts`  

**税务与主体演进**

- [ ] 引导高流水地摊办理个体工商户 / 食品许可，升级为正式二级商户  
- [ ] 提现与奖励发放保留完税所需字段

## 5. 技术实现方案（贴合本仓库）

### 5.1 状态机（建议落到 `merchants`）

```
入驻审核通过
  → pay_capability = none
  → 引导「开通收款」
       ├─ 进件成功：pay_capability = wx_sub_mch，写 wx_sub_mch_id
       ├─ 无证过渡：pay_capability = ledger_only（需开城开关）
       └─ 食品无证且卖热食：pay_capability = cash_disabled
```

下单前校验（`orderService` / `scan-pay`）：

1. `status=营业` 且 `feeService.assertCanTransact`（已有）  
2. 现金单：检查 `pay_capability` 与 `wx_sub_mch_id`  
3. `buildPayResult`：真实预下单；失败不入账  

### 5.2 模块改造清单

| 优先级 | 项 | 说明 |
| --- | --- | --- |
| P0 | 配置与限额 | `platform_config`：无证日限额、是否允许 ledger_only |
| P0 | 运营台 | 商户详情展示进件状态、无证标记、提现同名校验 |
| P1 | `wxPay` 服务 | JSAPI 下单、回调、退款（新建或扩展 `wxService`） |
| P1 | 分账任务 | 支付成功后异步分账；失败入重试表 |
| P1 | 进件工作流 | 小程序「开通收款」页 + 后台录入/查询二级商户号 |
| P2 | 对账任务 | 日切拉取微信账单与本地三表对平 |
| P2 | 类目风控 | 无食品证禁止部分 `stall_goods` 类目上架 |

### 5.3 与现有资金流对齐

```
消费者付款
  →（微信）二级商户入账 / 或台账路径平台代记
  → commission_ledger（平台抽成，应对齐微信分账金额）
  → merchant_accounts.cash_settlement（店应得）
  → withdraw_requests（台账路径）或微信结算到店主银行卡（二级商户路径）
```

积分路径不变：现金单仍按现有规则 `allocateToConsumer` 发积分，与是否有执照无关。

### 5.4 不建议的技术捷径

- 所有摊位共用同一个 `sub_mchid` 收款再内部分账 —— 违规且对账混乱。  
- 长期依赖 `wxpay_sim` 对外宣称已收款 —— 资金与客诉双爆。  
- 在未持牌情况下自建「余额当钱包、随意提现到任意人」—— 二清高危。

## 6. 场景决策表（给运营 / 产品直接用）

| 门店情况 | 能否入驻 | 能否上架 | 能否现金收款 | 推荐路径 |
| --- | --- | --- | --- | --- |
| 地摊：无执照、无食品证，已承诺 | 能 | 建议限制热食类目 | 过渡：台账限额；正式：个人经营者进件后 | D → B |
| 地摊：无执照，有食品证 | 能 | 相对宽松 | 个人经营者 / 个体户进件 | B |
| 地摊：已办个体户+许可 | 能 | 能 | 二级商户 | B |
| 异业：有执照 | 能 | 能 | 必须二级商户 | B |
| 异业/供应链：无执照 | **不能**（现规则） | — | — | 先办执照 |
| 任意：无二级商户且关闭 ledger_only | 能入驻 | 能 | **否**（仅积分相关） | E |

## 7. 一句话结论

- **业务上**：无证地摊可以按现有入驻与订单/台账逻辑跑通「收款体验」。  
- **资金上**：不能指望「申请一下平台微信支付就自动给无证摊位分款」；必须 **服务商收付通 + 每店（或每人）可结算主体**，无证只能走微信允许的个人经营者进件，或短期低额台账。  
- **最好落地**：**混合分层（方案 D）→ 全面二级商户（方案 B）**；用限额、同名结算、类目限制与开城白名单扛住过渡期风险；技术上补齐预下单、回调、分账、进件状态与对账，并与现有 `commission_ledger` / `cash_settlement` 对齐。
